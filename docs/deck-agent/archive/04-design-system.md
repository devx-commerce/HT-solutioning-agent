# 04 — Design system

The deck looks consistent because a designer decided how it looks once, in a
template, and the code refuses to deviate. The model's creativity goes into
*what to say and in what order*, never into where a box sits.

## The template deck

One Slides file in `sales.agent@`'s Drive, `TEMPLATE_FILE_ID`, built by a
human designer in the Slides UI. It carries:

- theme colors and fonts (inherited by everything we create)
- one custom **layout per archetype**, named predictably
- nothing else — no sample slides that survive into output

Every run copies it ([02](02-constraints.md) §1). A designer editing the
template changes every future deck with no code change. That property is worth
protecting: **never hardcode a font family or hex value** in
`updateTextStyle` unless deliberately overriding.

Store the template's layout ids and object-id conventions in a checked-in
`template_manifest.json`, regenerated by a script from
`presentations.get`. The compiler reads that, so a template change that
breaks an assumption fails loudly at build time rather than producing a
scrambled deck.

## Archetypes — the closed set

The planner picks from this list and nothing else. **Five in v1.**

| Archetype | Slots | For |
|---|---|---|
| `title` | client, title, subtitle, date | Opener |
| `statement` | headline, optional kicker | Section break, thesis, the one-line "so what" |
| `stat_callout` | headline, stat{value,caption}, support[≤3], visual? | A number that carries the argument |
| `two_column` | headline, left{…}, right{…} | Compare, before/after, problem/solution |
| `chart_focus` | headline, chart_spec, takeaway | The data slide |

Deferred to v2: `agenda`, `timeline`, `logo_wall`, `quote`, `table`,
`image_full`.

Five is enough to build a real pitch and small enough that every one can be
laid out well and genuinely tested. Adding a sixth is a day; adding a sixth
badly is a deck that looks wrong on slide 7.

## Design tokens

One checked-in file, `design_tokens.json`, read by the layout solver and the
chart renderer. Never read by the model.

```jsonc
{
  "canvas":  {"w_pt": 720, "h_pt": 405},      // 16:9
  "grid":    {"cols": 12, "gutter_pt": 12, "margin_pt": 36},
  "type": {
    "display": {"size": 40, "line": 1.15, "weight": 700},
    "h1":      {"size": 28, "line": 1.2},
    "body":    {"size": 18, "line": 1.35},
    "caption": {"size": 14, "line": 1.3},
    "micro":   {"size": 11, "line": 1.25}
  },
  "space":   {"xs": 4, "sm": 8, "md": 16, "lg": 24, "xl": 40},
  "palette": {
    "ink": "#12161C", "muted": "#5B6673", "paper": "#FFFFFF",
    "accent": "#C8102E", "neutral": "#C9D1D9",
    "good": "#0F7B4F", "bad": "#B3261E",
    "ramp": ["#C8102E", "#7A8794", "#C9D1D9", "#EDF0F3"]
  },
  "budgets": {
    "headline_chars": 90, "bullet_chars": 110, "bullets_max": 3,
    "words_per_slide": 55
  },
  "chart": {"bar_fill": 0.62, "label_col": 0.28, "value_gutter": 0.12}
}
```

The type scale is a **ladder, not a range**. The solver steps down it
(`display → h1 → body`) when text does not fit; it never picks an arbitrary
size. So every deck uses the same handful of sizes and looks like one system.

## Layout solving

Deterministic, ~150 lines, no model:

1. Archetype defines slot rects as grid spans (e.g. `stat` = cols 1–5,
   `support` = cols 7–12).
2. Resolve rects to points from `grid` + `canvas`.
3. For each text slot: measure the string with `fonttools`/PIL at the slot's
   token size, with real line-wrapping at the rect width.
4. If it overflows: step down the type ladder once. Still overflows: truncate
   at a word boundary with an ellipsis and **emit a flag**. Never silently
   overflow, never invent a size between ladder steps.
5. Emit final rects. Tier A then re-checks the result against the live deck,
   so a solver bug cannot ship silently.

## Standardize vs. leave to the model

| Fixed in code | The model decides |
|---|---|
| Grid, margins, safe areas | Narrative arc and slide order |
| Type ladder, fonts, weights | Headline wording — an assertion, not a topic label |
| Palette and semantic color roles | Which archetype fits which content |
| The archetype set | Chart type and what to plot |
| Element position and size | What to emphasize, what to cut |
| Font-size resolution, wrapping | Image concept and art direction |
| Chart geometry and styling | Speaker notes |
| Slide-count bounds, density budgets | Where the section breaks fall |

Creativity lives in **selection and sequencing**. That is what makes output
varied without ever being embarrassing.

## Deck-level consistency

Checked in Tier A, because slide-by-slide review cannot see these:

- no more than two consecutive slides sharing an archetype
- headline n-gram repetition across the deck below threshold
- one accent color per deck; ramp used only inside charts
- every slide's type sizes drawn from the ladder, no exceptions
- image style token identical across all generated images ([06](06-images.md))
